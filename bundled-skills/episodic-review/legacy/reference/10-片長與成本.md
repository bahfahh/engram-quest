# 10 片長與成本：短、中、長（完整）

> 又說：「這時間不要綁死，應該是一個 range。核心還是 AI token 花費，所以如果選擇簡短的，可以不用這麼精緻，專注在內容流程精簡點，運算時間快一點，以此類推。」
>
> 數字的唯一來源：`templates/length.json`。插件的設計說明：vault 的 `feature/feature-2026-11-02-episodic-review-plugin.md`。

## 1. 三檔是「花費的檔位」，不是固定秒數

選哪一檔，決定**這支片花多少 AI token 和算圖時間**：

| | 短 | 中 | 長（完整） |
|---|---|---|---|
| 主題數 | 1 | 2 | 3（內容需要可到 4） |
| 片長（範圍，不是目標） | 約 2～4.5 分 | 約 5～8 分 | 約 8～13 分 |
| 精緻度 | **精簡**：內容和流程講清楚，外觀用現成的 | **標準** | **精緻**：第三輪的完整做法 |
| 外觀 | 照用認可的外殼，不新做鏡頭、不調氛圍細節 | 外殼照用；只對 2～3 個最重要的鏡頭加工 | 氛圍做足（光、景深、轉場、色調） |
| 演示 | 只用 `assets/demos` 的現成元件換內容；沒有合適的就用筆記自己的圖 | 現成為主；每個主題最多新做 1 個 | 現成＋每個主題 2～3 個專屬演示 |
| 內容檔 | 只寫選中的 1 個主題的 10 項 | 2 個主題 | 完整 |
| 檢驗 | **自查**：`onscreen.py` 通過＋看一次定格；**不開**子 agent | 字的檢驗、畫面的檢驗各一次 | 兩種檢驗各兩階段，字卡抽定格確認讀得到 |
| 關鍵定格 | 3 張 | 6 張 | 8 張 |
| 解析度 | 1280×720（草稿大小） | 1920×1080 | 1920×1080 |
| 雲端 session | 通常 1（長到 4 分以上要 2） | 2～3 | 3～4 |
| 算圖牆鐘時間 | 約 40～70 分 | 約 40～70 分 | 約 40～70 分 |
| 相對 token（粗估，長 = 1） | 約 0.25 | 約 0.55 | 1 |
| 適合 | 第一次試看、只動了一個主題、只想複習最重要的一件事 | 一般的月回顧 | 月底完整回顧 |

- **「精簡」是少做精緻，不是少講內容**：深度優先的規則不變。選中的主題照樣走到筆記最深的那層、有演示、回想和揭曉；省的是氛圍細節、新寫的演示、檢驗的輪數。一個主題再壓也不低於約 2 分鐘。
- **片長是範圍**：照內容需要自然落在範圍裡；超出只是提醒（`onscreen.py` 印 `!`，不當錯誤），不要為了湊秒數硬砍或硬灌。
- **token 的主要來源**：讀筆記和寫內容檔（跟主題數成正比）、新寫的演示程式、開檢驗的子 agent（同類的一個子 agent 任務約 24～26 萬 token）、改幾輪。所以短版最省的是「不新寫演示」和「不開檢驗 agent」，不是只有主題數少。倍數是粗估；交付時記下這個 session 的 usage，累積後校正 `token_hint`。
- **算圖時間**：牆鐘時間不隨片長變長（每個 session 同時算 4 段），變多的是 session 數。短版用 1280 寬（`FARM_WIDTH=1280`）實測 3D 場景只快約 2 成（163 秒 → 128 秒），因為 3D 本來就用固定解析度算；所以省時間主要靠主題少。
- `scripts/length_estimate.py` 印出這張表；`--minutes 8` 找最接近的一檔。**只有這三個選項，沒有自訂**；長版的檔案可能逼近 GitHub 的 100 MB，`deliver.py` 會自動壓到上限內。

### 主題段不變，變的是外圍

主題段：進入＋情境 → 問題 → 主線演示（做法、案例、圖）→ 判斷規則 → 回想 → 揭曉 → 收束，各檔都一樣。外圍的預算：

| 段 | 短 | 中 | 長 |
|---|---|---|---|
| 片頭 | 4～6 秒 | 6 | 約 9 |
| 全貌 | ≤ 12 秒，只標走進去的那個 | ≤ 20 秒 | 約 30 |
| 主題段（每個） | 約 150～170 | 約 150～170 | 約 140～190 |
| 片尾（拿掉情境＋快問＋結尾） | 約 35（1 題） | 約 65（2 題） | 約 70（2 題） |

- 沒走進去的主題留在全貌當紋理（不用讀）。
- 短版裡，更正、懸案只在它就是這個主題的主線時才放；其餘留在筆記。
- 回想、揭曉的時間下限不縮（讀題＋6 秒、揭曉 ≥ 8 秒）。

## 2. 誰決定、怎麼問

**只有三個選項：短、中、長。** 順序：

1. **使用者這次已經說了，或插件的要求（`meta.json` 的 `requests`）裡帶了片長** → 照說的，不再問。對照：

   | 使用者說 | 當成 |
   |---|---|
   | 「完整」「長版」「10 分鐘」「3 個主題」 | 長 |
   | 「中版」「6、7 分鐘」「2 個主題」 | 中 |
   | 「短版」「簡短」「快一點」「省一點」「3 分鐘」「只做一個」「只做 X 那個主題」 | 短（主題指定 X） |
   | 「X 和 Y 兩個」 | 中（主題指定 X、Y） |
   | 其他分鐘數或主題數 | 換成最接近的一檔，告訴使用者換算結果 |

2. **沒說、而且能問使用者**（目前測試階段都是這樣）→ **讀完內容後，直接問一次要哪一檔**（`AskUserQuestion`，三個選項）。每個選項的說明寫：主題數、片長範圍、精緻度、雲端 session 數、算圖時間、相對 token；把建議的那一檔放第一個並標「建議」，理由寫在說明裡（例如「這個月有 2 個主題寫到做法」）。這一問同時就是開工前的確認，不再另外問。
3. **沒說、又不能問**（自動排程）→ 讀插件設定 `episodicLength`；沒有就用預設「中」；選擇寫在報告第一段。

插件設定只有一個欄位（`.obsidian/plugins/engram-quest/data.json`，照現有的平的命名；缺少就用預設；skill 只讀、不寫）：

| 欄位 | 值 | 預設 |
|---|---|---|
| `episodicLength` | `short` / `medium` / `long` | `medium` |

其他一律不設定：**主題照第 3 節排名自動挑**，估算和選檔位在同一個問題裡問。設定太多沒意義。

## 3. 什麼時候問、怎麼挑主題

1. **步驟 2 讀完內容後才問**：先知道哪些主題夠深（顆粒度到 L3 以上），建議才有根據。夠深的 ≥ 3 建議長、= 2 建議中、≤ 1 建議短。
2. 使用者選的檔位比夠深的主題多時，老實說（「這個月只有 2 個主題寫到做法，長版會有一個只講到 L2」），讓使用者決定，**不自己補內容湊主題**。
3. **挑主題**（使用者沒指名時，依序比）：顆粒度（L4 > L3 > L2）→ 有現成的圖或專案案例 → 彼此的內容和演示方式不重複 → 這個月動的量（只當平手判斷）。順序照筆記動的先後。
4. **第一階段報告要有**：檔位和估算（`length_estimate.py`）、選的主題和理由、**沒選的主題清單**（下一支的候選）。

## 4. 工具

- `film.json` 加 `"length": "short|medium|long"`；`onscreen.py` 比對主題數和片長範圍，超出只印提醒。
- `plan_parts.py <秒數> --sessions auto --out-prefix <路徑>/parts-<id>`：一次產出每個 session 的段清單。
- 短版算圖：`FARM_WIDTH=1280 bash scripts/farm.sh …`（`render.cjs --width 1280`；版面仍照 1920×1080 排，只有輸出變小）。
- 短版檢驗從簡，**不是不檢驗**：`onscreen.py` 要過、關鍵定格有字和遮字各看一次；發現外殼的畫面太弱就升一檔，不要硬做。

## 5. 續集

沒走進去的主題，下一支再做。第一階段報告的「沒選的主題清單」就是候選；下個月的 `collect.py` 也會標出還沒做的主題（`09-重用與加速.md` 第 3 節）。

## 6. 還沒定、等使用者決定

- `token_hint` 是粗估，等累積幾支片的實際 usage 再校正。
- 短版要不要保留 1 題片尾快問（目前保留，因為「拿掉情境再問一次」是這支片的記憶機制）。
