資料庫索引為什麼能那麼快？

從「一頁一頁翻」到「直接翻到那一頁」——目錄的魔法
1

它解決什麼問題

資料表沒有索引時，找「王小明」只有一個辦法：從第一列讀到最後一列（全表掃描）。一百萬列就翻一百萬次，而且下次查還是重翻一遍。

📄📄📄📄📄

沒索引：全表掃描

一列列翻，100 萬列翻 100 萬次 😫
資料量翻倍 → 時間翻倍
📖🔖

有索引：查目錄

先查目錄「王 → 第 573 頁」，直接跳過去 😎
資料量翻倍 → 只多翻一次目錄
同一個查詢，兩種世界：O(n) vs O(log n)
2

它在整趟查詢的哪一站

一句 SQL 下去之後，資料庫內部其實有一趟旅程。索引影響的是「決定怎麼找」那一站：

🧑‍💻 你送出 SELECT ... WHERE name='王小明'
↓
🧭 查詢優化器：「有 name 的索引嗎？」→ 有就走目錄，沒有就硬翻
↓
💽 磁碟讀取（真正花時間的地方）
↓
📬 回傳結果
索引不加速磁碟本身——它讓你「少讀非常多次」磁碟
3

記憶紙

🏷 主視覺記憶錨
📕✋🔖
索引 = 字典側邊的部首目錄
查「豬」沒有人從第一頁翻起——先摸側邊的凹槽目錄，一手翻到那個部首。
索引就是幫資料表裝上這排凹槽。
4

目錄的三層魔法

地基

為什麼「翻」那麼貴？資料存在磁碟上，每讀一「頁」都是一次 I/O，這是資料庫世界最貴的動作。全表掃描 = 把幾十萬次 I/O 硬吃下去。所以一切加速的本質只有一句話：想辦法少讀幾頁。

關鍵一步

排序讓「用猜的」變成可能。電話簿為什麼好查？因為它照姓名排好了——你翻到中間，看到「林」，就知道「王」在前半，一次砍掉一半範圍（二分搜尋）。索引 = 把某個欄位抽出來排好序，旁邊記著「本尊在第幾頁」的指標。100 萬筆資料，砍半 20 次就到了。

B-TREE 金字塔

目錄太厚，就替目錄再做一層目錄。百萬筆的索引本身也很厚，於是 B-tree 把它疊成金字塔：

📖 總目錄（王在左邊・陳在右邊）
↙↘
📑 王～林📑 陳～黃
↙↘
📄 王小明 → 第573頁📄 …
樹疊 3～4 層就能蓋住千萬筆資料 → 任何查詢只要 3～4 次 I/O

代價也在這裡：每次 INSERT / UPDATE，這座金字塔都得同步改——所以索引越多，寫入越慢、空間越肥。索引是「用寫入成本和空間，換讀取速度」的交易。

5

三個最常踩的誤解

⚠️「索引越多越好」？每個索引都是一座要同步維護的金字塔。寫入頻繁的表掛滿索引，INSERT 會慢到你懷疑人生。只為「真的會拿來查」的欄位建。
⚠️LIKE '%明%' 為什麼救不了？目錄是照「開頭」排序的。查「姓王的」一翻就到；查「名字裡有明的」等於把整本字典重翻一遍——開頭萬用字元讓索引直接失效。
⚠️「主鍵」和「索引」是同一件事？主鍵自動附帶一個索引（所以主鍵查詢快），但索引不必是主鍵——任何常查的欄位都能另外建。一張表一個主鍵、可以多個索引。
